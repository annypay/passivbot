# g4 @ TWE 3.0 的账户级守护实测：一周 −20% 熔断与阶梯升级

本文件是研究的跨 arm 综合结论；每个 arm 的完整深度分析（仓库报告规范固定骨架 + 研究附录，含“账户守护读数”与“整装待发读数”）在其自己的 run 目录 `annual_analysis.md` 中。

## 一、问题、条件映射与方法

上一轮已证明：**无守护的 10,000 USDT / TWE 3.0 在本地历史里于 2021-05-19 被强平**（窗口开始后 29.5 天）。本轮给同一配置加一层账户级守护，回答它能不能“大难不死、还能整装待发”。

### 你的条件 → 引擎配置映射

| 你的条件 | 引擎口径 | 配置 | 说明 |
|---|---|---|---|
| 账户级 | unified 作用域 | `live.hsl_signal_mode=unified + bot.long.hsl.enabled=true` | backtest 直接读取 live.hsl_signal_mode（src/backtest.py） |
| 一周内 | 滚动峰值窗口 7 天 | `live.pnls_max_lookback_days=7.0` | 分母 = 窗口内最高策略权益；含已实现亏损，比“纯浮亏”更保守 |
| 浮亏 20% | RED 阈值 20% | `bot.long.hsl.red_threshold=0.20` | 触发指标 min(raw, EMA)；引擎硬约束 red <= no_restart <= 1.0 |
| 立即反应 | 快速 EMA | `bot.long.hsl.ema_span_minutes=60` | 默认 720 分钟正是上一轮“0 次触发就被强平”的原因 |
| 熔断 12H / 升级 24H | 停机时长（单一常量） | `bot.long.hsl.cooldown_minutes_after_red=720 或 1440` | 阶梯本身不可表达；近似见 restart_after_red_policy=threshold + no_restart_drawdown_threshold |
| 第二次按剩余余额再算 20% | episode 结束后滚动峰值清空 | `无需配置` | 第二次触发天然以停机后的剩余权益为峰值基准（rolling_peak_strategy_pnl.clear()） |

### 引擎分层语义（已逐条在代码里核实）

| 档位 | 行为 |
|---|---|
| orange | 整个作用域进入 TpOnly：不产生任何新入场（含加仓），只走止盈路径 |
| red | 先 Panic 平掉整个作用域，再停机 cooldown_minutes_after_red |
| yellow | 仅遥测（不改变交易模式） |

- 峰值窗口由 `live.pnls_max_lookback_days` 控制，本轮守护臂统一设为 7 天（=“一周内”）。
- 判定规则：**J1** 任一守护 arm 在 5.4 年腿 liquidated=false 且活到窗口末 ⇒ 判定“账户级守护在本地历史上确实能挡住同一次崩盘”，并记录是哪个配置与代价；若全部强平 ⇒ 判定在 TWE 3.0 这一档账户级止损来不及。；**J2** 3 年腿上任一守护 arm 同时满足“最差回撤 ≤ 无守护基线 × 0.8”与“CAGR ≥ 无守护基线 − 30pp” ⇒ 通过（收益代价可接受）。；**J3** 同一阈值下对比停机时长（12H vs 24H）：更长的停机在强平/最差回撤/复牌后表现上不更差 ⇒ 判定阶梯升级值得做；否则不值得。；**J4** g_soft_orange 或 g_orange_only 在回撤与终值上同时优于直译版 g_user12h ⇒ 推荐“先停加仓、后清仓”的分级方案；否则直译版已足够。；**J5** g_slow_ema 的 hard_stop_triggers ≈ 0 且结果与无守护基线一致 ⇒ 判定“触发速度”是必要条件，并把它写进结论第一条。
- 控制臂为上一轮的两条无守护运行（`twe300_10k__3y` / `twe300_10k__ext`），其 `analysis.json` sha256 已钉住、不重跑。

- 机制结论：账户级守护要起作用，前提是**触发要快**（EMA 60 分钟级）并且**在加仓链条上先动手**（ORANGE/TpOnly 停加仓）；因为 TWE 3.0 满仓时到强平地板只有约 −31.8%——如果崩盘是跳空式的，任何账户级止损都来不及，真正决定生死的仍是暴露上界本身。
- 本次新增的一条硬教训：`no_restart_drawdown_threshold` 的锁存判定发生在**平仓确认那一刻**、用的是 `max(raw, EMA)`，所以急跌里“先到 20% 触发、确认时已经跌过 40%”会把带终局阈值的臂**在第一次触发就永久关停**——`g_ladder40__ext` 就是这样：活下来了，但也彻底退出了。要长期经营，终局阈值必须严格高于“一次急跌的确认回撤”，或者改成“累计已实现亏损”口径。
- 组合建议（按优先级）：① 先把 TWE 收到可控范围（本轮全部 arm 都在 TWE 3.0 这一档，属高风险实验）；② 若保留 TWE 3.0，至少加“−20% 停加仓 + 更深阈值清仓 + 永久地板”这套分级守护，并把永久地板设在“确认回撤”之上；③ 想要真正的“大难不死”，结构性去风险（`we_excess_allowance_pct=0`、下调 TWE）比任何熔断都可靠。
- 本轮的阶梯只是近似（引擎的冷却时长是单一常量）；引擎级阶梯、冷却后部分复入、与日线闸门联动见 `account_guard_design.md`，需要独立 PR。

## 十、边界

- 任何账户级止损都挡不住“超过到强平距离的跳空”：TWE 3.0 满仓时到地板只有约 −31.8%，所以真正的黑天鹅防线仍是结构（TWE/we_excess_allowance_pct/n_positions）+ 快触发 + 分级反应。
- 引擎的冷却时长是单一常量，无法表达“第二次升级为更长时间”的阶梯；本轮用 restart_after_red_policy=threshold + no_restart_drawdown_threshold 做终极端近似，并在 account_guard_design.md 给出引擎级设计方案。
- RED 的语义是“先 panic 平掉整个作用域、再停机”，因此“熔断”= 实现亏损 + 离场；“只停机不清仓”只能通过 ORANGE/TpOnly 表达（停加仓、保仓位、只止盈）。
- “浮亏 20%”在引擎口径下是“策略权益相对 7 天滚动峰值回撤 20%”，包含已实现亏损，比纯未实现亏损更保守；报告显式声明该解释。
- 历史范围有限：币池是活到 2026 年的当前 top40（幸存者偏差），5.4 年腿 2021-04-20 起交易、当时仅 22 个币有数据；2021-05 事件落在闸门首次风险开启后 3 个交易日。
- 未建模：真实资金费率、滑点枯竭、API 断连、交易所/稳定币对手方风险；引擎不模拟保证金占用。
- 引擎级增强（阶梯冷却、按剩余余额重设的第二级、冷却后部分复入、与日线闸门联动）的设计与风险写在 `account_guard_design.md`，需要独立 PR + 实盘重建契约 + 测试矩阵。
