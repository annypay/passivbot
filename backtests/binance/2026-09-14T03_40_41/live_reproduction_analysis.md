# 默认 Trailing Martingale 策略：实盘复现深度分析

## 范围与结论

本报告分析 `configs/examples/default_trailing_martingale_long.json` 在 Binance
USDT-M 永续合约上的**实盘运行逻辑**，并与同一配置在本工件目录的三年
Binance 1 分钟回测交叉参照。分析仅阅读配置、源码和回测工件；没有启动机器人、
读取账户、使用密钥、调用认证接口或提交/撤销任何订单。

**结论一：不是 41 个币种同时交易。** 配置中的 41 个 long 币种是候选池。正常
运行时，Rust 会保留已有仓位的管理，再从合格的平仓候选中填补最多 7 个 long
仓位槽位。因而它会持续观察、计算和排名大量币种，但正常目标不是同时新开 41 个
仓位。

**结论二：这是 long-only、高风险的追踪马丁格尔组合。** short 的
`total_wallet_exposure_limit` 为零，不能建立策略空仓；long 组合允许最高
150% 钱包敞口，且默认没有启用 HSL 权益硬止损。策略依赖分散的币种选择、
回撤加仓、反弹/回落确认式的追踪出场和 auto-unstuck 来处理风险，不能将三年
回测的增长结果理解为实盘回报承诺。

**结论三：该示例文件不能直接当作 Binance 实盘配置。** 回测时使用的
`-e binance` 仅覆盖 `backtest.exchanges`，与实盘账户没有关系。模板的
`live.user` 是 `bybit_01`；实盘连接器按此标识解析账户所属交易所。若要复现为
Binance，必须先在 Git 忽略的私有配置中显式绑定一个 Binance 账户标识，并经
单独授权后才可能发生认证或交易所配置动作。

## 41 个候选币如何变为最多 7 个正常仓位

### 活动标的集合并非持仓集合

每个执行循环的 Python 侧活动集合会合并以下标的：

1. 交易所已报告的仓位；
2. 交易所已报告的开放订单；
3. 逐币覆盖项；
4. 当前获批准、未忽略、可解析且允许新开仓的币种。

因此，在没有仓位时，机器人仍可能为接近全部候选池维护行情、已完成 1 分钟 K
线、EMA 和排名输入。这是为了能在空槽出现时决定哪个币有资格开仓，并不表示会为
每个币发布 entry。

### forager 的筛选顺序

long 侧在本配置满足 forager 条件：TWEL 大于零、没有强制模式、`7 < 41`。Rust
按下列顺序处理：

1. 已持有且受机器人管理的 long 始终列为 active；即使历史遗留仓位数已经大于
   7，也继续管理它们，不能因重新排名而放任不管。
2. 若还有空槽，先纳入强制为 normal 的标的；然后才考察普通候选。
3. 普通候选必须通过交易所可交易性、币龄（默认至少 60 天）、最小有效成本、当前
   盘口、EMA 和 forager 特征完整性等检查。缺少必要特征不是以零分代替，而是没有
   新开仓资格。
4. 在排名确有必要时，先按 `volume_drop_pct = 0.04` 剔除成交量最低尾部，但永远
   至少保留空槽数量；随后对保留候选做归一化评分：
   `0.21 × EMA 就绪度 + 0.61 × 波动率 + 0.18 × 成交量`。
5. 分数最高的“剩余空槽数”个币被选中。已有入选币有 2% 分数滞回：
   挑战者优势不足时保留 incumbent，以减少频繁换币和撤挂单。

当没有 long 仓位且候选均可用时，`slots_to_fill` 是 7；已有 3 个正常 long 时，
初始选择只填 4 个。若 7 个槽已被现有仓位占满，常规 forager 不会再选择新的
平仓标的。manual 仓位不属于机器人策略范围，不消耗策略 active 槽位；而受机器人
管理的历史仓位可能使实际受管理数量暂时超过 7，这也是“7”应理解为正常目标并发
数而非可忽略风险的绝对上限的原因。

## Long 侧下单策略的实际含义

### 初始 entry

新选中的平仓标的会走 long 的初始 entry 路径。配置的
`entry.ema_gate_mode = "all"`，所以初始 entry、部分初始 entry 和后续 re-entry
都会受到 EMA 带约束。价格 EMA 使用 790 和 1080 分钟跨度，初始门槛
`initial_ema_dist = 0.0028`；盘口价格不在允许范围时，Rust 不产生初始 entry，
空槽可保持未使用。

首笔目标量以单币有效 WEL、`initial_qty_pct = 0.0081`、当前余额、标的合约乘数
和当前限价计算，再按交易所的价格步长、数量步长及最小数量/最小名义额约束处理。
因此，首笔金额不是固定 USDT 值，也不是简单的“七等分 150%”。

### 回撤加仓与追踪确认

持有 long 后，entry 的 `retracement_base_pct = 0.0008` 大于零，策略使用追踪
马丁格尔而非静态网格：

1. 以均价为锚，价格先出现向下的阈值偏离，阈值基数为 1.9%，并由当前 1 分钟/
   1 小时波动率、现有仓位 WEL 比率调节；
2. 之后从该次低点反弹达到所需 retracement，才产生下一笔 long entry；
3. 新量由 `double_down_factor = 0.94`、初始量和可用 WEL 共同计算；如预计成交
   后超出可用单币预算，则裁剪数量；
4. 每次同币同侧增加仓位都会重置追踪极值，并启动 24.1 分钟冷却，因此不会在一轮
   快速行情中无间隔地连续加仓。

这不是传统“每跌固定比例就把仓位翻倍”的无界马丁格尔。它仍是均价下移/回撤加仓
策略，风险核心在于趋势下跌时会积累敞口、等待反弹，并受单币及组合预算约束。

### 出场、减仓与 trailing 状态

long close 同样是阈值加 retracement 的追踪逻辑。`close.retracement_base_pct =
0.0005`，`close.qty_pct = 0.84`；阈值基数为 -0.27%，并受 1 分钟/1 小时波动率
和 WEL 权重影响。最终阈值小于等于零时，追踪从开仓后立即有效；大于零时，需先有
足够上行，再在高点后的回撤达到确认幅度。触发后按当时 ask 和步长形成 reduce-only
long close。由于阈值与仓位暴露相关，Rust 可以递归模拟部分 close 后的敞口，生成
不同价格的 close 梯子，而不是假设一个固定止盈价。

Python 依据已完成的 K 线、最近的仓位/成交变更锚点持续重建四个状态：
`max_since_open`、`min_since_max`、`min_since_open` 和 `max_since_min`。它们是
Passivbot 自己计算的策略状态，不是向 Binance 提交交易所原生 trailing-stop。
同币同侧任意成交会使该追踪窗口重置；若无法从可靠的成交锚点和连续 K 线重建，
依赖该状态的 entry/close 分支不会产生普通理想订单。

### 非常规风险减仓

HSL 未启用，故本配置没有常态化的权益硬止损。然而 auto-unstuck 已启用：
`threshold = 0.466`、`close_pct = 0.041`、`loss_allowance_pct = 0.0052`，
并要求独立 EMA 门控。满足条件时它是 Rust 的保护性 reduce-only 意图，执行优先级
高于普通订单。WEL/TWEL 自动 enforcer 则均为关闭状态，所以不能将 auto-unstuck
误解为“超仓必定自动全平”。同时 `max_realized_loss_pct = 1` 是已实现亏损门控的
极高上限，不是 100% 账户回撤止损。

## 组合风险：7 槽、WEL、TWEL 与杠杆不可混为一谈

单币基础 WEL 为约 21.43%。37% 超额容许可使单币策略计算的有效 WEL 接近
29.36%，用于处理步长、最小成本和策略的尾部加仓空间；`bounded` 模式要求它仍
受总 TWEL 约束。若七个标的都试图达到各自的有效上限，合计约为 205.5%，因此
这是不允许的：Rust 会把已有仓位和候选 entry 都按“成交后”的钱包敞口重算，
排序/删减候选，必要时二分裁剪最后可容纳的订单数量，确保总数低于组合上限。

实际敞口还会随价格、均价、可用余额、合约乘数、部分成交和交易所步长变化。交叉
保证金与 10 倍杠杆只影响交易所保证金安排和可持有名义规模；它们不会把
`total_wallet_exposure_limit = 1.5` 变成低风险仓位，也不会取代爆仓、维持保证金、
资金费、手续费和流动性风险评估。

## Binance 账户语义：策略 one-way 与交易所 hedge mode

`live.hedge_mode = false` 在本策略中表示 Rust 不应在同一标的同时建立策略 long 和
short 敞口。由于 short 侧本已禁用，当前实际策略为 long-only。

Binance 连接器仍会把 Binance 合约账户配置为 Hedge Mode，并在每张订单上明确发送
`positionSide = LONG` 或 `SHORT`，以稳定识别仓位和 reduce-only 语义。对 long：

| 动作 | Binance `side` | `positionSide` | 机器人含义 |
|---|---|---|---|
| 建/加 long | `BUY` | `LONG` | 增加 long 敞口 |
| long 平仓/减仓 | `SELL` | `LONG` | reduce-only 语义 |

首次为某个标的创建会增加敞口的订单之前，执行管线还可能请求该标的采用配置的 cross
保证金和 10 倍杠杆。上述账户模式、保证金和杠杆设置都是认证的交易所写操作，不能
把它们当作无副作用的“预览”。

## 一次实盘循环的可复现链路

1. **权威账户刷新。** 每轮以新的刷新 epoch 获取并核对余额、仓位、开放订单；
   fill/PnL 历史在当前风险消费者需要时也纳入。余额、仓位或开放订单任一项无效，
   普通计划和交易动作不会继续。
2. **准备 universe 与风险预算。** 刷新批准/忽略列表、交易所可交易性、最小有效
   成本和 WEL；加入已有仓位和开放订单，避免在重启或部分成交后遗失管理对象。
3. **刷新市场与指标。** 维护已完成的 1 分钟 K 线，计算 entry/close、forager 和
   unstuck 所需的 EMA/波动率；持仓标的还重建 trailing extrema。
4. **获取新鲜盘口快照。** 以当前 bid/ask/last 和时间戳构成市场快照。快照在交给
   Rust 前与本轮账户 epoch 绑定，并对待操作标的校验新鲜度和符号集合。
5. **Rust 生成完整理想订单。** 输入包括余额、仓位、盘口、交易所精度和最小值、
   EMA、trailing 状态、冷却成交时间、策略参数与所有风险开关。Rust 依次管理已有
   仓位、选择空槽候选、计算 entry/close，并将 TWEL/WEL、unstuck 等约束整合为
   当前批次的完整目标订单集。
6. **生产者边界验证。** Python 对 Rust 输出做严格校验：符号、方向、订单类型、
   价格/数量有限性、限价精度、entry/close 合法性、执行类型和优先级、同侧累计
   reduce-only 数量均须与输入一致。畸形或不完整输出是 fatal，不能回退到上一轮
   ideal orders。
7. **订单调和。** 将理想订单转为带 `side`、`position_side`、`reduce_only`、
   client ID 和执行类型的订单，与权威开放订单逐标的比较。精确匹配的订单保留；
   过期订单进入撤单，缺失订单进入创建。配置的 0.0002 匹配容差会抑制微小价格/
   数量差引发的无意义撤挂。
8. **执行门控。** 低余额时禁止增加敞口但允许撤单和保护性 close；账户状态在计划
   后变化、市场快照变旧、刚提交过相同订单、所需交易所配置未确认或 churn 门控
   拦截时，普通创建会被延后。对于同一风险作用域的撤挂，先撤单并等待权威确认后
   再重新规划创建，避免旧新订单重叠。
9. **有限批次执行与确认。** 保护性 reduce-only 撤单优先。每批上限为 5 个撤单和
   3 个创建；发送后要求开放订单权威刷新确认。取消时若交易所返回“已成交/已取消”
   这类竞争状态，也会要求更完整的账户确认，而不是假设本地状态正确。

本配置禁用普通市价执行，但 `GTC` 不是 maker-only。回测中的 1 分钟触价结果不能
保证 GTC 在实盘一定以 maker 成交；盘口跨越、网络延迟和撮合队列都可能使实际费率、
成交价格和成交顺序改变。

## 重启、断线和状态重建

| 状态/事件 | 权威或可重建来源 | 重启后的处理 |
|---|---|---|
| 余额、仓位、开放订单 | 交易所账户状态 | 刷新成功前不进行普通交易；恢复后以真实状态重算理想订单。 |
| 已发布订单 | 交易所开放订单 + client ID | 不依赖旧进程内存；调和后保留匹配订单、撤掉不再理想的订单。 |
| entry 冷却 | 最近增加仓位的成交历史；必要时仓位增量守卫 | 以短期 fill 历史重建；未知数据不能伪造为“无冷却”。 |
| trailing 极值 | 最近仓位/成交锚点后的连续已完成 K 线 | 重新计算；若重建边界或数据不可靠，相关普通分支不下单。 |
| forager incumbent/短期 churn 记忆 | 内存中的运行时优化状态 | 可在重启后重置；已持仓仍优先管理，新的平仓选择重新排名，真实订单以交易所快照调和。 |
| 交易所临时不可用标记 | 内存、带过期时间 | 重启后重新探测，不永久继承旧的本地拒绝结论。 |
| 创建/撤销请求超时或响应不完整 | 交易所后续权威刷新 | 标记为模糊状态，阻止相同方向的盲目重复创建，等待确认和重新规划。 |

进程级异常会清理客户端后尝试重建机器人；正常重启冷却为 60 秒，且默认一天最多
10 次。这个机制只能恢复进程，不会消除市场风险或确保连接恢复期间的保护性限价单
一定成交。

## 失效时的行为边界

设计原则是“缺少关键输入则不伪造中性值”。最重要的边界如下：

- 余额、仓位、开放订单是账户关键面；其中任一面不可用时，普通交易 fail closed。
- 对平仓候选缺少 forager EMA、成交量或波动率特征时，该候选失去新 entry 资格，
  不会被用虚构零值排名。
- 单个标的缺少普通策略 EMA 或 trailing 重建数据时，影响该分支的普通 entry/close
  不生成；调和会删除已不再有 Rust 理想意图的普通挂单。独立满足输入要求的
  protective reducer 可继续。
- Rust 输出非有限、违反交易所约束、累计 close 超过当前仓位或与输入策略不一致时，
  在连接器调用前终止，而不是沿用缓存订单。
- 外部或另一实例的 Passivbot 订单会被识别为并发控制风险；账户不应让两个机器人
  对同一合约集合竞争。

这些安全门控更擅长避免“在未知状态下继续加仓”，但它们也会在市场剧烈变化或行情/
账户数据暂不可用时延迟普通订单更新。因此，不能把“失败时不新增风险”误解成
“已有仓位已被保证保护”。

## 三年回测能复现什么，不能复现什么

### 与实盘共用、可审计的部分

- 策略类型、long 参数、forager 权重、7 槽逻辑、WEL/TWEL 风险计算、追踪极值语义、
  订单类型和 Rust 订单生成器属于同一策略内核；
- 本工件中的 Binance-only 数据集使用 1 分钟蜡烛；回测有效覆盖率为 100%，且使用
  40 个可用标的；
- 回测没有发生强平，最终总余额为 1,118,097.20 USDT，起始余额为 100,006.78 USDT，
  `gain_usd = 11.087553`，仅说明该段历史和模拟成交规则下的结果。

### 不能由该回测承诺的部分

| 回测中可控的假设 | 实盘额外变量 | 对本策略的影响 |
|---|---|---|
| 1 分钟 OHLC 触价和模拟成交 | 撮合队列、盘口深度、部分成交、拒单、最小值变化 | 追踪确认与多级 entry/close 的实际顺序、数量和平均价可能不同。 |
| 历史 candle 连续可用 | WebSocket/REST 延迟、短缺口、交易所维护 | EMA/trailing/forager 可能被局部延后或失去新 entry 资格。 |
| 固定回测费率与成交模型 | maker/taker 身份、实际手续费、资金费和滑点 | `GTC` 不保证 maker，净收益可能显著低于模拟值。 |
| 单一确定性回放 | 当前币龄、上/下架、市场状态、账户余额和外部订单 | 实盘的候选集合、选币结果和有效 WEL 每轮都可变。 |
| 无进程故障的统一时间线 | 网络中断、响应模糊、节流、重启 | 订单更新会被安全门控、确认和批次上限延迟。 |

更重要的是，历史曲线本身已经显示出很高的路径风险：最差 USD/strategy-equity
回撤为 **73.69%**，最大峰值恢复期为 **172.60 天**，最长单仓持有约 **165.78 天**，
平均组合 TWEL 约 27.41%、历史最大约 1.50017（浮点/取整附近），三年内有
69,537 笔成交、约 63.45 笔/日。PnL Sharpe 为 0.4302、Sortino 为 0.9230。
这些数据意味着，即使没有发生回测强平，也存在长时间深度浮亏、成交频繁和对费用/
执行质量敏感的现实风险。

## 实盘复现的判定标准

若未来获得明确的实盘授权，能称为“同策略复现”的最低条件应是：

1. 使用私有、非跟踪配置将 `live.user` 显式绑定 Binance，而不是依赖本模板的
   `bybit_01` 标识；保留策略和风险参数，并单独审查任何账户级差异。
2. 启动前能够从交易所获得一致的余额、仓位和开放订单；标的通过币龄、市场状态、
   最小有效成本和完整指标检查。
3. 日志/监控能看到 forager 的候选数、rankable 数、选中币、剩余槽位、组合 TWEL、
   各仓位 WEL/WELe、挂单调和、拒绝/延后原因和权威确认结果。
4. 对比回测时，记录真实 maker/taker 费率、资金费、滑点、部分成交、订单生命周期、
   延迟和停机窗口；它们是评估是否仍然“行为一致”的必要证据。
5. 风险承受能力必须覆盖回测中 73.69% 回撤及更差的尾部情形。尤其应单独决定是否
   保持 HSL 关闭、150% TWEL 和 10 倍杠杆这一组合，而不能只依据最终收益倍数。
