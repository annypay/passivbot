# 0005 — g4 @ TWE 3.0 的账户级守护：一周 −20% 熔断 12H / 升级 24H 实测（2026-09-17）

这份记录回答一个直接的问题：**在 `0004` 已经证明“TWE 3.0 / 10,000 USDT 会被强平”之后，加一层账户级守护
（一周内浮亏 20% ⇒ 熔断 12H；第二次按剩余余额再算 20% ⇒ 熔断 24H）能不能做到“大难不死、还能整装待发”？**
它同时给出三条对照：软刹车（只停加仓不砍仓）、纯停加仓、慢触发，以及“累计 40% 永久停机”的阶梯近似。

它属于研究记录；实盘相关事项仍在 `0002-binance-live-debug-2026-09-17.md`。

## 结论先行（数字与完整表格见 `backtests/binance/g4_twe300_account_guard_2026-09-17/account_guard_analysis.md`）

1. **你的条件在本地历史上确实救回了账户。** 5.4 年历史压力腿上，无守护臂 2021-05-19 12:53Z 被强平（0.71×、回撤 95.34%）；
   `unified` + RED 0.20 + EMA 60 分钟 + 停 12H 的直译臂 **7.86×、最差回撤 62.40%、存活到窗口末**（5 次停机、合计 55 小时）。
   它在 12:47 完成 panic 清仓，比无守护臂触及地板早 **6 分钟**。
2. **但“熔断”在这套引擎里 = 实现亏损 + 离场，且方向性风险是真实的。** 第一次复牌后 7 天 **−13.5%**，
   4 天后第二次触发（05-23，停机起点全期回撤 54.6%）。整装待发是“能再来一次”，不是“能接着赚”。
3. **“只停加仓、不砍仓”的软刹车被证伪。** ORANGE=0.20/TpOnly 的两个 arm（RED 0.35、RED 0.60）
   在历史腿 `hard_stop_triggers = 0`，**443 笔成交与无守护臂逐笔相同、终值逐位相同（0.7139×）**——
   一次都没触发就强平了。ORANGE 只阻止新入场，已经堆到 3× 的仓位照样跟着崩到地板。
4. **触发速度是必要条件。** 同一套阈值把 EMA 拉长到 720 分钟，历史腿 0 次触发、同样强平（J5）。
5. **“累计 40% 永久停机”这个阶梯近似是危险的。** `g_ladder40__ext` 的锁存判定发生在 panic 平仓**确认那一刻**、
   用 `max(raw, EMA)`；触发线是 20%，但确认回撤已经 46.9% ≥ 0.40，于是**第一次触发就永久关停**：
   账户没被强平（0.57×、回撤 57.57%），但 2021-05-19 之后再没交易过（停机 1942 天、占窗口 98.5%）。**“未强平”不等于“还活着”。**
6. **温和窗口的代价必须一起看**：3 年腿上直译守护把终值 8.8346× 压到 6.2161×（−30%），
   CAGR 106.69% → 83.84%，最差回撤 31.60% → 30.19%（几乎没改善），最长恢复期 31 → 99 天。
   同期 `g_soft_orange__3y` 几乎不伤收益（8.6169×、CAGR 104.98%），但它就是第 3 条里被强平的那个配置。
7. **停机时长 ≠ 离场时长**：24H 臂在 05-23 那次冷却到期后又空仓等了 **17 小时**才等到入场信号
   （实际离场 41h，离场/声明 = 1.18）。按“熔断 24H”估算资金占用会偏低。
8. **拉长冷却没有证据支持**（J3 两腿均“更差”）：24H 的复牌后 7 天表现与最差回撤都不优于 12H。

## 方法

- 父配置：`backtests/binance/g4_twe300_10k_replay_2026-09-17/artifacts/g4_twe300_10k.config.json`
  （即 `0004` 的 TWE 3.0 / 10,000 USDT 配置，sha256 冻结），本轮的 12 个 arm 只声明守护相关差异
  （`bot.long.hsl.*`、`live.hsl_signal_mode`、`live.pnls_max_lookback_days=7.0`）。
- 12 个预注册 arm = 6 种守护 × 2 条腿（原生 3 年 / 5.4 年历史压力腿）；控制臂是 `0004` 的两条无守护运行，
  `analysis.json` sha256 钉住、不重跑。
- 每个 arm：冻结配置 → 离线重放（`src/backtest.py`，命中冻结 bundle、无取数标记）→ 深度分析
  （仓库报告规范固定骨架 + 研究附录：账户守护读数、整装待发读数）→ 独立复核（`verify_variant_report.py`，
  不 import 渲染器，逐行复算停机窗口）。
- **停机窗口的推导口径**（写进每个 arm 的 `guard_readiness.json`）：紧跟 panic 平仓（≤180 分钟）之后、
  权益恒定（容差 1e-6 USDT）且无成交的连续段；结束后有成交 = 完整停机（止于复牌成交），
  结束后再无成交 = **终局停机**（止于回测结束）。窗口与 `cooldown_minutes_after_red`
  （终局停机则与 `hard_stop_duration_minutes_max`）比较，容差两个采样格（120 分钟）；
  超出部分记为“停机结束后等待入场信号的空仓时间”。`cross_check_problems` 只在关系不可能成立时报错，
  并与 `hard_stop_triggers` / `hard_stop_restarts` / `hard_stop_time_in_red_pct × 窗口` 交叉校验。
  **首版推导曾把“panic 之后 22.6 小时的普通空仓段”误计为一次停机**（24 小时的 panic 关联窗口太宽），
  现已收紧到 180 分钟并加了回归测试。
- 跨 arm 综合 `account_guard_analysis.md` + `verify_synthesis.py` 独立复核；12/12 arm 与综合全部通过。
- 离线：无网络、无凭据、不启动实盘；所有 arm 关闭逐币成交面板（内存），报告逐 arm 声明。

## 引擎口径（读数字前必须知道）

- 分层：YELLOW 仅遥测；**ORANGE = 整个作用域 TpOnly（不产生任何新入场、含加仓，只走止盈）**；
  **RED = 先 panic 平掉整个作用域、再停机**。因此“停机但保留仓位”在这套引擎里不可表达。
- 触发指标 `min(raw, EMA)`；`no_restart_drawdown_threshold` 用 `max(raw, EMA)` 判定，且在**平仓确认那一刻**求值。
- “浮亏 20%”在本引擎口径下 = “策略权益相对 **7 天滚动峰值**回撤 20%”，**包含已实现亏损**；
  报告表格里的“停机起点回撤”是**全期运行峰值**口径，两者分母不同，不可混读。
- 到强平地板只有 `起始资金 × (1 − 0.05)`，在满仓 3.0× 处 ≈ **−31.8%** 行情：这是账户级止损可保险区间的上界。

## 对实盘决策的影响

- **不因本轮结论而放宽 TWE。** 守护把“清零”变成“重伤”（95% → 62% 回撤）是真实收益，但它不是安全边际；
  满仓 3.0× 的跳空风险仍然没有对手方。
- **若坚持 TWE 3.0：用直译守护，不要用锁存。** `unified` + RED 0.20 + ORANGE 0.15 + EMA 60 + 停 12H +
  `no_restart_drawdown_threshold=1.0`（不永久停机）。终局阈值必须严格高于“一次急跌的确认回撤”。
- **不要把 ORANGE 当黑天鹅防线**；它只是加仓节奏控制，崩盘里救不了已经堆起来的仓位。
- **结构性去风险仍然优先**：`0004` 已验证 `we_excess_allowance_pct=0` 在同一条历史腿上未被强平
  （14.29×、回撤 92.22%），终值高于本轮任何守护臂，且不需要盯盘。
- 本记录不改发布 profile；若决定改守护参数，另开 profile PR 并同步 `docs/strategy_profiles.md` 与 `0002` 的启动清单。

## 待办与后续

- **引擎级增强需要独立 PR**（设计见 `backtests/binance/g4_twe300_account_guard_2026-09-17/account_guard_design.md`）：
  ① 阶梯冷却（12h → 24h → 72h，按滚动窗口内的触发次数）；② 冷却后分级复入（避免“一次满仓复牌”）；
  ③ 以**累计已实现亏损**为口径的预算式停机（替代 RAW 尖峰锁存）；④ 与日线闸门联动（risk-off 期间延长冷却）。
  每一条都需要实盘重建契约与测试矩阵。
- 复牌时点值得单独研究：本轮 12H 臂的首个复牌 7 天是 −13.5%，说明“固定冷却时长”与“市场是否还在下跌”无关；
  候选做法是“冷却到期 + 近期创新低则顺延”，但这会延长离场时间，需要用本轮同一套管线量化代价。
